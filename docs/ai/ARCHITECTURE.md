# Mercer — архитектура для AI-агентов

## Цель документа

Этот документ описывает границы компонентов Mercer, разрешённые направления
зависимостей и основные потоки данных. Используйте его, чтобы определить место
для изменения и не переносить ответственность между сервисами случайно.

- `docs/ai/PROJECT.md` объясняет назначение проекта и навигацию по репозиторию.
- Этот файл объясняет, как связаны компоненты и где должна жить логика.
- `docs/ai/CONVENTIONS.md` определяет правила реализации и проверки изменений.
- Детальная документация в `context/` остаётся источником истины для конкретных
  маршрутов, DTO, данных и поведения сервисов.

## Контекст системы

```text
Клиент / Frontend
        |
        | HTTP
        v
   rag-backend --------------------> rag-indexer
        |                                 |
        |                                 +--> parser / embeddings
        |                                 +--> pdf-sidecar
        |                                 +--> db-api-server
        |
        +--> db-api-server -----------> индексные документы и чанки
        +--> PostgreSQL (rag-db)
        +--> Redis
        +--> LLM и embedding providers
        +--> host-agent
```

`rag-backend` — прикладная точка оркестрации пользовательских сценариев.
`rag-indexer` отвечает за подготовку и индексирование документов.
`db-api-server` — API-граница доступа к индексным данным, документам, чанкам и
поисковым операциям. `pdf-sidecar` изолирует специализированную обработку PDF.

В Docker Compose `rag-indexer` является внутренним сервисом: его порты не
публикуются наружу, а доступ к нему выполняется из `rag-backend` во внутренней
сети. Не меняйте эту границу без отдельной архитектурной задачи.

## Границы компонентов

| Компонент | Владеет | Не должен делать |
|---|---|---|
| `rag-backend` | Прикладные HTTP-сценарии, RAG-оркестрация, retrieval, генерация, pipelines и update-mode | Обращаться к индексному хранилищу в обход `db-api-server`; реализовывать ingestion |
| `rag-indexer` | Ingestion, parsing, chunking, embeddings, запуск и отслеживание индексирования | Реализовывать пользовательские RAG-сценарии backend |
| `db-api-server` | API-операции над индексными документами, чанками, поиском и хранилищем | Содержать RAG-оркестрацию, UI-логику или доменную логику backend |
| `pdf-sidecar` | Извлечение и специализированную обработку PDF | Владеть индексацией, поиском или прикладным API |
| `shared_contracts` | Общие DTO, сериализуемые модели и межсервисные контракты | Содержать бизнес-логику отдельного сервиса |
| PostgreSQL | Реляционные данные и миграции backend | Заменять векторное/чанковое хранилище |
| Redis | Состояние и координацию, необходимые backend и indexer | Быть долговременным источником доменных данных |

## Разрешённые зависимости

Разрешённое направление зависимостей:

```text
Frontend -> rag-backend
rag-backend -> rag-indexer
rag-backend -> db-api-server
rag-backend -> PostgreSQL, Redis, LLM providers, host-agent
rag-indexer -> db-api-server, Redis, pdf-sidecar, embedding providers
Любой сервис -> shared_contracts
```

Следующие зависимости запрещены без явного архитектурного решения:

- `rag-backend` не импортирует внутренние модули `rag-indexer` или
  `db-api-server`.
- `rag-indexer` и `rag-backend` не обходят API `db-api-server` для работы с
  индексными документами и чанками.
- `db-api-server` не зависит от прикладных сервисов `rag-backend`.
- `shared_contracts` не импортирует сервисные модули и не зависит от конкретной
  инфраструктуры.
- Компоненты не обмениваются данными через общие локальные файлы или
  незафиксированные побочные таблицы вместо согласованного API/контракта.

## Потоки данных

### Индексация документа

```text
Документ
  -> rag-indexer
  -> parser и pdf-sidecar при необходимости
  -> нормализация, chunking и embeddings
  -> db-api-server
  -> индексные документы и чанки
```

Вопросы parsing, разбиения на чанки, embeddings, повторной индексации и
состояния обработки принадлежат `rag-indexer`. Вопросы сохранения,
восстановления, поиска и чтения сохранённых чанков принадлежат `db-api-server`.

### Обычный RAG-запрос

```text
Клиент
  -> rag-backend
  -> поиск через db-api-server
  -> retrieval и, если применимо, reranking
  -> сборка контекста
  -> LLM
  -> ответ клиенту
```

RAG-оркестрация, выбор контекста и формирование ответа остаются в
`rag-backend`. Доступ к поисковым и документным данным выполняется через API
`db-api-server`.

### Pipeline и update-mode

```text
Клиент
  -> rag-backend / pipeline executor
  -> retrieval
  -> при запросе полного документа:
       db-api-server: GET /index/document/{id}/chunks?vault_id={vault_id}
       -> реконструкция текста
  -> LLM
  -> запланированные файловые операции и применение изменений
```

Режим полного документа — часть RAG-логики backend. Полный текст
восстанавливается из чанков через DB API, а не чтением внутреннего хранилища.
При изменениях этого пути проверяйте retrieval, ограничение контекста,
обработку ошибок, параллелизм и сценарии update-mode.

## Владение данными и контрактами

- PostgreSQL хранит реляционные сущности backend. Его миграции находятся в
  `rag-backend/migrations`.
- `db-api-server` владеет API-доступом к индексным данным, документам и чанкам.
- `shared_contracts` является единственной точкой для моделей, передаваемых
  между сервисами.
- Новый JSON-поле, enum, обязательность поля или изменение семантики может быть
  breaking change: найдите и обновите всех производителей и потребителей.
- Сервис-владелец отвечает за валидацию, хранение и обратную совместимость.
  Потребитель не должен угадывать отсутствующие поля или тихо менять их смысл.

## Инфраструктура и конфигурация

| Переменная | Потребитель | Назначение |
|---|---|---|
| `DATABASE_URL` | backend, indexer | Подключение к PostgreSQL |
| `DB_API_URL` | backend | URL `db-api-server` |
| `STORAGE_API_URL` | backend, indexer | URL API индексного хранилища (`db-api-server`) |
| `INDEXER_API_URL` | backend | URL `rag-indexer` |
| `REDIS_URL` | backend, indexer | URL Redis |
| `ENCRYPTION_KEY` | backend, indexer | Шифрование API-ключей моделей |
| `WATCHDOG_INTERVAL_SEC` | indexer | Интервал watchdog |
| `HOST_AGENT_URL` | backend | URL host-agent |

Не фиксируйте в коде реальные значения секретов, токены, ключи или локальные
адреса. Новая переменная окружения требует обновления `.env.example`, Compose,
конфигурационного кода и документации, если она обязательна для запуска.

## Правила архитектурных изменений

1. Локальная бизнес-правка остаётся в сервисе-владельце.
2. Изменение межсервисного формата начинается с поиска всех производителей и
   потребителей и обновления `shared_contracts` при необходимости.
3. Изменение RAG-пайплайна требует проверки retrieval, сборки контекста,
   token budget, ошибок и релевантных тестов pipeline/update-mode.
4. Изменение DB API требует проверки endpoint, клиентов backend/indexer,
   схемы ответа, обработки ошибок и производительности на объёме данных.
5. Перенос логики между сервисами — отдельное архитектурное изменение, а не
   попутный рефакторинг.
6. При расхождении кода и документации не выбирайте версию молча: укажите
   конфликт, проверьте историю и тесты, затем уточните ожидаемое поведение.
