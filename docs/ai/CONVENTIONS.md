# Mercer — соглашения разработки для AI-агентов

## Назначение и приоритеты

Этот файл определяет, как AI-агент должен вносить изменения в Mercer.

Приоритет источников истины:

1. Явная задача и уточнения пользователя.
2. Применимые документы из `context/`.
3. `docs/ai/PROJECT.md` и `docs/ai/ARCHITECTURE.md`.
4. Существующий код, тесты и фактическое поведение системы.

Если источники противоречат друг другу:

- не выбирай версию молча;
- укажи расхождение кратко;
- проверь связанных потребителей и тесты;
- запроси уточнение, если поведение нельзя определить из задачи.

## Режимы работы

### Когда пользователь просит анализ или план

Не меняй файлы.

Верни краткий ответ:

1. Затронутые файлы и компоненты.
2. План максимум из трёх пунктов.
3. Риск или блокер — только если он есть.

Не пересказывай задачу, код или документацию без необходимости.
Не показывай chain-of-thought и подробные внутренние рассуждения.

### Когда пользователь явно просит изменить код

Сразу вноси изменения в editable-файлы.

- Не ограничивайся планом, листингом, псевдодиффом или описанием решения.
- Не жди дополнительного подтверждения, если пользователь явно не попросил
  сначала составить план.
- Возвращай edits только в формате, который ожидает текущий режим aider.
- Не пытайся редактировать read-only-файлы.
- Если нужный файл не добавлен как editable, кратко попроси пользователя
  добавить его через `/add` или перезапустить aider с этим файлом.
- Если задача требует изменения нескольких файлов, редактируй все необходимые
  editable-файлы в одной связной правке.

После успешной правки отвечай максимум четырьмя короткими пунктами:

1. Что изменено.
2. Какие файлы изменены.
3. Какие проверки запущены и их результат.
4. Непроверенная область, риск или блокер — только если есть.

Не выводи полный листинг файлов, полный diff или подробные рассуждения, если
пользователь явно не запросил их.

## Рабочий цикл

Перед изменением:

1. Определи затронутые сервисы, контракты, данные и пользовательский сценарий.
2. Прочитай только применимые документы из `context/`.
3. Найди существующую реализацию и тесты.
4. Выполни минимальное связное изменение.
5. Добавь или скорректируй тест, если поведение меняется или исправляется bug.
6. Запусти релевантные проверки вручную, если пользователь не попросил иначе.

Не смешивай функциональное изменение с несвязанным рефакторингом,
переименованием или массовым форматированием.

## Область изменения

- Изменяй только файлы, необходимые для текущей задачи.
- Не создавай абстракции, базовые классы, helpers или зависимости «на будущее».
- Не меняй публичные сигнатуры, типы возврата, JSON-поля, переменные окружения
  или семантику API без анализа всех потребителей.
- Не удаляй комментарии, проверки и обработку ошибок без понимания их причины.
- Не исправляй несвязанные предупреждения и не форматируй весь файл ради
  локальной правки.
- Сохраняй существующий стиль, именование, структуру модулей и типизацию.

## Асинхронность и I/O

Mercer использует асинхронные сервисы. Не блокируй event loop.

- Не вызывай блокирующие операции, синхронный сетевой I/O, тяжёлые операции с
  хранилищем или CPU-bound вычисления напрямую из `async def`.
- Для существующего синхронного API используй согласованный async-адаптер,
  например `asyncio.to_thread()`, когда операция должна выполняться вне event
  loop.
- Переиспользуй существующие HTTP-клиенты. Не создавай `httpx.AsyncClient` на
  каждый запрос.
- Закрывай клиентов и ресурсы через lifecycle приложения.
- Используй `asyncio.gather()` только для независимых операций.
- При параллельной работе явно обрабатывай частичные ошибки, таймауты,
  отмену задач и закрытие ресурсов.
- Не убирай существующий параллелизм без причины и не добавляй новый
  параллелизм без ограничений и обработки ошибок.

## API, данные и контракты

- Валидируй входные данные на границе сервиса.
- Изменение JSON-поля, enum, обязательности, формата ошибки или семантики
  endpoint — потенциально breaking change.
- Перед изменением контракта найди всех производителей и потребителей.
- Синхронно обновляй модели, сериализацию, валидацию, API, клиентов, тесты и
  документацию.
- Общие межсервисные DTO и модели размещай в `shared_contracts`.
- Не добавляй в `shared_contracts` бизнес-логику конкретного сервиса.
- Не обходи `db-api-server` прямым доступом к индексным документам и чанкам.
- Не добавляй fallback, который молча принимает несовместимый контракт.

## Ошибки, логи и безопасность

- Не используй `except: pass`, пустые обработчики исключений и правдоподобные
  значения по умолчанию, которые скрывают сбой.
- Разделяй ошибки валидации, ожидаемые внешние сбои и внутренние дефекты.
- Сохраняй исходную причину через `raise ... from exc`, если преобразуешь
  исключение.
- Логируй контекст операции и безопасные идентификаторы сущностей.
- Не логируй секреты, токены, пароли, содержимое `.env` и ненужный текст
  пользовательских документов.
- Не понижай уровень ошибок до `debug`, чтобы скрыть проблему.
- Не отключай валидацию, авторизацию, проверки целостности или сканирование
  секретов ради прохождения теста.

## Тесты и проверки

Основные команды проекта:

```bash
make lint
make test
```

- Не утверждай, что проверка прошла, если команда не запускалась.
- Для исправления bug добавляй регрессионный тест, если сценарий можно
  воспроизвести надёжно.
- Для изменения API проверяй успешный сценарий, валидацию и релевантные ошибки.
- Для async-кода проверяй ошибки, отмену и частичный успех там, где это важно.
- Для pipeline и update-mode проверяй пустой результат, частичные ошибки,
  повторный запуск, лимиты контекста и итоговый результат.
- Сначала запускай наиболее узкий тестовый модуль.
- Затем запускай `make test`, если окружение и время позволяют.
- При невозможности запуска сообщай точную команду, причину и непроверенную
  область.

## Документация

Обновляй документацию вместе с кодом, если меняются:

- API, DTO или формат данных;
- обязательная конфигурация или переменные окружения;
- схема данных и миграции;
- поведение RAG-пайплайна, ingestion, PDF-обработки или update-mode;
- архитектурные границы сервисов.

Детали поведения храни в `context/`.
Обновляй `docs/ai/` только при изменении устойчивых правил работы агента,
архитектурных границ или навигации по проекту.

## Git

- Не выполняй `git add`, commit, push, создание ветки, тега или PR без прямого
  запроса пользователя.
- Не выполняй `git reset`, `git checkout`, `git clean`, force-push или другие
  разрушительные команды без отдельного явного подтверждения.
- Не отменяй чужие изменения и не пытайся очистить dirty working tree.
- Когда пользователь прямо просит создать коммит, используй короткое сообщение
  в стиле Conventional Commits: `feat:`, `fix:`, `refactor:`, `perf:`,
  `test:` или `docs:`.
- Сообщение коммита пиши в императивной форме, на русском и не длиннее
  72 символов.

## Запрещённые практики

- Не добавляй зависимости, сервисы, хранилища или инфраструктурные слои без
  явной необходимости.
- Не дублируй код между сервисами вместо контракта или общего компонента.
- Не переноси ответственность между компонентами как побочный эффект локальной
  правки.
- Не меняй API, схему БД, миграции или переменные окружения без оценки
  обратной совместимости.
- Не добавляй секреты, токены, ключи, реальные учётные данные или локальные
  пути в код, тесты, документацию и логи.
- Не выдавай текстовый листинг или план за выполненную правку.
