# Mercer — соглашения разработки для AI-агентов

## Назначение и приоритеты

Этот файл задаёт практические правила внесения изменений в Mercer. Он отвечает
на вопрос «как безопасно менять код», а не описывает архитектуру или предметное
поведение.

Приоритет источников истины:

1. Явная задача и уточнения пользователя.
2. Документы в `context/`, особенно `context/conventions.md`.
3. `docs/ai/PROJECT.md` и `docs/ai/ARCHITECTURE.md`.
4. Существующий код и тесты.

Если источники расходятся, не выбирайте версию молча. Укажите конфликт,
проверьте связанных потребителей и тесты, затем запросите уточнение, если
ожидаемое поведение нельзя вывести из задачи.

## Рабочий цикл

Перед изменением:

1. Прочитайте `docs/ai/PROJECT.md`, `docs/ai/ARCHITECTURE.md` и применимые
   документы из `context/`.
2. Определите затронутые сервисы, контракты, данные и пользовательский
   сценарий.
3. Найдите существующую реализацию, её вызовы и тесты до создания новых
   модулей, моделей или endpoint.
4. Выполните минимальное связное изменение, полностью решающее задачу.
5. Добавьте либо скорректируйте тесты для изменённого поведения, когда это
   практически возможно.
6. Запустите подходящие проверки вручную и сообщите точные результаты.

Не смешивайте функциональное изменение с несвязанным рефакторингом,
форматированием или переименованием.

## Изменения Python-кода

- Следуйте локальному стилю модуля: структуре, именованию, типизации и
  обработке ошибок.
- Используйте ясные имена и небольшие функции с одной ответственностью.
- Не добавляйте абстракцию, базовый класс, helper или dependency «на будущее».
  Сначала найдите существующий аналог.
- Не меняйте публичные сигнатуры, типы возврата или семантику функции без
  анализа всех вызовов.
- Не удаляйте комментарии, проверки и обработку ошибок, пока не доказано, что
  они устарели.
- Не исправляйте несвязанные предупреждения и не форматируйте весь файл ради
  одной правки.

## Асинхронность и I/O

Mercer использует асинхронные сервисы. Не блокируйте event loop.

- В `async def` не вызывайте блокирующие операции, синхронный сетевой I/O,
  тяжёлые операции с хранилищем или CPU-bound вычисления напрямую.
- Для существующего синхронного API используйте согласованный адаптер, например
  `asyncio.to_thread()`, если работа действительно должна выполняться вне event
  loop.
- Переиспользуйте существующие HTTP-клиенты. Не создавайте
  `httpx.AsyncClient` на каждый запрос; закрывайте клиент через lifecycle
  приложения.
- Используйте `asyncio.gather()` только для независимых операций. Явно
  определяйте обработку частичных ошибок и не теряйте исключения.
- Не заменяйте конкурентную реализацию последовательной без причины и не
  добавляйте параллелизм без лимитов, обработки ошибок и проверки нагрузки.
- Учитывайте отмену задач, таймауты, закрытие ресурсов и идемпотентность
  повторного вызова.

## API, модели и контракты

- Валидируйте входящие данные на границе сервиса.
- Изменение JSON-поля, enum, обязательности, формата ошибки или семантики
  endpoint — потенциально breaking change.
- Перед изменением контракта найдите всех производителей и потребителей.
  Синхронно обновите модели, сериализацию, валидацию, API, клиентов, тесты и
  документацию.
- Общие межсервисные DTO и модели размещайте в `shared_contracts`; не переносите
  туда сервисную бизнес-логику.
- Не обходите `db-api-server` прямым доступом к индексным данным и чанкам.
  Например, восстановление полного текста выполняется через API DB server, а
  не через внутренние детали хранилища.
- Не добавляйте fallback, который молча принимает несовместимый контракт.

## Ошибки, логи и безопасность

- Не используйте `except: pass`, пустые обработчики исключений или
  правдоподобные значения по умолчанию, скрывающие ошибку.
- Разделяйте ошибки валидации, ожидаемые внешние сбои и внутренние дефекты.
- При преобразовании исключения сохраняйте исходную причину через
  `raise ... from exc`, если это применимо.
- Логируйте контекст операции и безопасные идентификаторы сущностей, но не
  секреты, токены, пароли, содержимое `.env` и ненужный текст пользовательских
  документов.
- Сохраняйте существующие уровни и формат логов; не снижайте уровень ошибок до
  debug, чтобы «очистить» вывод.
- Не отключайте валидацию, авторизацию, проверки целостности или сканирование
  секретов ради прохождения теста.

## Тесты и проверки

Основные команды запускаются вручную:

```bash
make lint
make test
```

Конфигурация aider отключает автоматический lint и автоматический запуск
тестов. Это не означает, что проверки не нужны.

- Для bug fix добавляйте регрессионный тест, когда сценарий можно надёжно
  воспроизвести.
- Для API-изменения проверьте положительный сценарий, валидацию входных данных
  и релевантные ошибки.
- Для async-кода используйте существующий тестовый подход и проверяйте ошибки,
  отмену либо частичный успех там, где это важно.
- Для изменения pipeline или update-mode проверьте пустой результат, частичные
  ошибки, повторный запуск, лимиты контекста и формирование результата.
- Сначала запускайте наиболее узкий тестовый модуль, затем более широкий набор
  или `make test`, если окружение и время позволяют.
- Не утверждайте, что тесты или lint прошли, если команда не запускалась.
  Сообщайте команду, результат и непроверенную область.

## Документация

Обновляйте документацию вместе с кодом, когда меняются:

- HTTP API, DTO или формат данных;
- конфигурация, обязательные переменные окружения или Compose-состав;
- схема данных и миграции;
- поведение RAG-пайплайна, ingestion, PDF-обработки или update-mode;
- архитектурные границы и направления зависимостей.

Используйте `context/` для детального описания поведения. Обновляйте
`docs/ai/` только при изменении устойчивых правил работы агента, архитектурных
границ либо проектной навигации.

## Git и область изменений

- Не выполняйте `git add`, не создавайте коммит, ветку, tag, PR и не делайте
  push без прямого запроса пользователя.
- Не выполняйте `git reset`, `git checkout`, `git clean`, force-push и другие
  потенциально разрушительные действия без отдельного явного подтверждения.
- Не отменяйте чужие изменения и не пытайтесь «очистить» рабочее дерево.
- Изменяйте только файлы, необходимые для задачи.
- Когда пользователь явно запрашивает коммит, используйте короткое сообщение в
  стиле Conventional Commits: `feat:`, `fix:`, `refactor:`, `perf:`, `test:`,
  `docs:` или подходящий scope. Сообщение — в императивной форме, на русском и
  не длиннее 72 символов.

## Запрещённые практики

- Не добавляйте зависимость, новый сервис, хранилище или инфраструктурный слой
  без явной необходимости и обоснования.
- Не дублируйте код между сервисами вместо согласованного контракта или общего
  компонента.
- Не переносите ответственность между компонентами как побочный эффект локальной
  правки.
- Не меняйте API, схему БД, миграции или переменные окружения без оценки
  обратной совместимости.
- Не добавляйте секреты, токены, ключи, реальные учётные данные или локальные
  пути в код, тесты, документацию и логи.
- Не заявляйте о выполнении команд, проверок или ручного тестирования, которых
  не было.
